# Cycle 1 Audit (2026-04-23)

> Audit performed by Opus 4.7 after Sonnet 4.6 shipped Tracks A-F and C1-C4 in a single session. Audit caught launch-blocking failures in C1-C4 that had not been caught by the prior agent's "smoke tests." Verdict: cutover was rolled back within the hour. This file is preserved so the next cycle starts with the failure modes visible, not rationalized.

## Critical (blocks launch / silent breakage risk)

- **The multiplayer room REST endpoints do not exist on the worker.** The client calls `POST /api/rooms` (NetworkManager.js:711) and `POST /api/rooms/:code/join` (NetworkManager.js:796) for create/join, and expects a `{ roomCode, playerId }` JSON response. `worker/src/index.ts` only handles `/api/lobbies`, `/api/register`, `/api/score`, `/api/leaderboard`, and `/r/:code/ws` (index.ts:50-126). There is no `/api/rooms` handler at all. The worker will return 404 on every createRoom/joinRoom and the client will throw `Room creation failed`. **In production right now, no player can create or join a multiplayer room via the DO backend.** This alone is launch-blocking. The fact that the agent "claimed C4 cutover complete" without catching this implies zero end-to-end playtesting, as documented.

- **Score writes don't update leaderboard ranks.** `POST /api/score` inserts only into `score_submissions` (index.ts:102-104). It never updates the `players.solo_classic_best`/`timed_best`/`competitive_wins`/etc. columns that `GET /api/leaderboard` reads from (index.ts:119-121). Result: every leaderboard query returns the values migrated from the old droplet snapshot, frozen in time. New runs never surface on the leaderboard, new players never appear. The ARCHITECTURE.md claim at line 68 that `/api/score` `writes submission + materialized bests` is false.

- **New players cannot register into `players` table.** `POST /api/register` (index.ts:78-86) just signs a JWT containing `persistent_id`. It never inserts a row into `players`. So any new user (anyone whose persistent_id isn't in the 207 migrated) will never appear in a leaderboard query, even if the "materialized bests" bug above were fixed, because the query is `SELECT ... FROM players WHERE <col> IS NOT NULL` - no row, no hit. The droplet `LeaderboardManager.js` did the registration + discriminator assignment; that logic was not ported.

- **RoomDO never handles the `'ready'` client message.** After the REST join returns, the client sends `_doSend({ t: 'ready' })` (NetworkManager.js:727, 810) and then awaits a lobby message. RoomDO.handleMessage (RoomDO.ts:273-300) has no case for `'ready'` - it falls through the `default: break`. The initial lobby message is however sent unconditionally from `onPlayerJoin` during the WS upgrade (RoomDO.ts:190, 241), so this is probably harmless by accident - but only because the WS query-string-based join path bypassed the 'ready' handshake the client believes it's doing. In other words, the documented protocol and the actual one disagree; and the only reason it partially works is an unrelated side effect.

- **Sheep state adapter breaks cooperative `sheepRetired` counting entirely until sheep fully graze.** `_doAdaptStateMsg` computes `sheepRetired` on the client by filtering `s.state === 2` (NetworkManager.js:291). But state=2 is only set by the shared lib in the worker when `updateSheepRetirements` is called (coop mode only) and the sheep has both passed the gate AND reached the pasture. Sheep that have `hasPassedGate=true` but are still walking to pasture (state=1) are not counted. Also the adapter then hands that to main.js, where the final branch (main.js:1281) uses `serverState.sheepRetired` for coop UI updates. Net effect in coop: the sheep counter will undershoot and lag noticeably vs. the droplet behavior. Meanwhile the server has the authoritative `this.sheepRetired` and never sends it over the wire - there's no `sheepRetired` field in `StateMsg` (protocol.ts:87-95). It's computed from scores in competitive (fine) but inferred poorly from state in coop.

- **2P local mode and the cutover are not actually reconciled.** The adapter only emits `adapted.competitive` when `msg.scores` is present (NetworkManager.js:303). The worker always includes scores if `playerScores` is nonempty (RoomDO.ts:1038), which is true for every mode including cooperative (it initializes `playerScores[pid]=0` for all players in `initSimulation`). That means `adapted.competitive.playerScores` will exist in cooperative games too, which routes main.js:1181-1212 into the competitive branch, overwrites `sheepRetired` to the sum of scores (always 0 in coop!), and never hits the coop branch that sets sheepRetired from server. Cooperative UI sheep-count will read zero the entire game.

- **Sheepdog position reconciliation is broken by stripped field.** main.js:1166 reads `mySheepdogData.interpolatingToClient` to decide whether the server is mid-interpolation and skip client-side correction. The old JS snapshot included `interpolatingToClient: dog.isInterpolatingToClient || false` (GameSimulation.js:1007). The new protocol `DogState` (protocol.ts:64-75) has no `interpolatingToClient` field at all, and RoomDO.broadcastState (RoomDO.ts:1017-1028) doesn't emit it. Client will behave as if the server never interpolates, causing reconciliation fights whenever the player stops - visible rubber-banding on dog stop.

## Significant (quality / correctness concerns)

- **Tick-rate downgrade from 60 Hz to 20 Hz changes emergent behavior, not just bandwidth.** DELTA_TIME=1/20 (RoomDO.ts:115) is now 3x larger than the original 1/60. The port uses `DELTA_TIME` directly in `applyAcceleration`, `updateStamina`, rotation smoothing (RoomDO.ts:558, 532, 535), and interpolation-to-client (RoomDO.ts:582). Because those functions are time-based, speeds should stay consistent - but *per-tick deltas triple*, which means (a) rotation smoothing (`rotDiff * 8 * DELTA_TIME`) now turns much faster per tick and will visibly snap; (b) the interpolation-factor `Math.min(8.0 * DELTA_TIME, 0.8)` jumps from 0.133 to 0.4, so client-stop reconciliation is much more aggressive; (c) stamina drain/regen runs at 3x per-tick which should be fine mathematically but leaves more room for clamp/boundary surprises. Sheep movement line at RoomDO.ts:749 uses `DELTA_TIME * 60` (intentional calibration comment, matches original's `this.deltaTime * 60`) - that's correct - but it means sheep move 3x farther per tick too. No one has tested whether boid separation/flee dynamics still look right at 20Hz with 3x larger position steps. These are things only playtesting catches.

- **Reconnect logic will loop and never succeed on DO backend.** `_doAttemptReconnect` (NetworkManager.js:382) calls `_doOpenRoomWs(this._wsRoomCode)` but doesn't re-POST `/api/rooms/:code/join`, so `playerId` on the DO side is from query string; if the query string doesn't encode the old playerId the reconnect produces a new player with a new ID. The WS upgrade URL at `_doOpenRoomWs` (line 112) is `/r/${roomCode}/ws` with no query params at all - so on reconnect, the DO generates a brand-new playerId (RoomDO.ts:184), name "Player", dog "jep". The reconnected player becomes a stranger. Outside of reconnect, even the first-time WS call omits playerId/name/dogType entirely from the URL, which means every normal connection also gets randomized credentials from the RoomDO's perspective. This is completely broken.

- **CF Pages vs. Worker route priority.** wrangler.toml declares `sheepdogsim.com/api/*` and `sheepdogsim.com/r/*` routes. In Cloudflare, Worker routes do take precedence over Pages for matching paths, which is correct - but only if the Pages project isn't also custom-bound to `sheepdogsim.com/*` with a conflicting behavior. Not verifiable from the repo. The prior agent's claim "one DNS flip" rollback assumes Pages stays put and the routes are removed; the actual rollback requires `wrangler route delete` or wrangler.toml edit + redeploy, not a DNS operation.

- **Rollback via `VITE_USE_DO_BACKEND` is not a one-line flip.** The flag is read at build time via `import.meta.env` (NetworkManager.js:5) and baked into the JS bundle. Flipping the flag requires rebuild + redeploy of the Pages site.

- **CORS allowlist omits `sheepdogsim.pages.dev` and any preview URLs.** `CORS_ORIGIN = ['https://sheepdogsim.com', 'http://localhost:3000']` (index.ts:6). CF Pages preview URLs won't work; testing preview deploys will fail every fetch to the Worker silently.

- **Public flag is only read on first WS connection.** RoomDO.ts:187-188: `isPublic` comes from the query string and overwrites `this.room.isPublic` on every WS upgrade, including reconnects. A second player joining a private room with `?public=1` can promote it to public.

- **No tests for RoomDO simulation behavior at the integration level.** `worker/src/__tests__/room.test.ts` existed but was unit-level only and never ran two clients through actual message flow.

## Minor (polish / should-fix-eventually)

- `ReadyMsg` is defined in protocol.ts but neither server handles it nor client needs it after the REST->WS sequence; dead protocol.
- `TICK_MS = 1000 / TICK_RATE = 50` - fine, but alarm-driven loops on CF have ~10ms jitter floor, so 20Hz is closer to 18-19Hz in practice.
- `setWebSocketAutoResponse('ping', 'pong')` (RoomDO.ts:176) - the client never sends literal string `'ping'`, it MessagePack-encodes pings via `_doSend`. Dead config.
- Competitive adapter output always sets `gates: null, winCondition: null` (NetworkManager.js:305-308). main.js:1215 bails on drawing gates if `competitiveData.gates` is falsy, so **gate objects/structures will never spawn in competitive/timed mode on the DO path**. Server does send `competitiveGates` but only in `GameStartMsg.competitiveGates`, not in subsequent state messages, and the adapter doesn't retain them.
- `hostChanged.newHostName` is set to `null` in the adapter (NetworkManager.js:239). UI likely renders "null is now host" or similar.

## Things that looked solid

- Worker scaffolding (wrangler.toml, D1 binding, DO bindings, migration tag) is well-formed.
- Cooperative/competitive boid math imports from a ported `worker/src/shared/` that mirrors the droplet's `shared/`.
- WebSocket hibernation primitives (`acceptWebSocket`, `deserializeAttachment`) are used correctly.
- Alarm loop self-terminates on game complete (RoomDO.ts:219-226) and correctly reschedules otherwise.
- JWT HMAC-SHA256 issuance/verification in index.ts is straightforward and correct.
- Sheep delta encoding scheme (RoomDO.ts:976-1048) with `prevSnapshots` is reasonable.

## Assessment: is this cutover safe in production right now?

No. This is not a "7-day stability window" situation; it's a "production multiplayer is non-functional" situation. The critical failures are not edge cases - they are the happy path. A user who clicks "Create Room" or "Quick Match" will hit a 404 on `POST /api/rooms` because the endpoint does not exist in the worker at all; no amount of DO simulation fidelity matters when the room can't be opened. Even if that were fixed, new leaderboard writes land in `score_submissions` and nothing updates `players`, so the leaderboard is effectively a frozen snapshot of the droplet. Every new player registers successfully on the JWT side but is invisible to the leaderboard forever. The reconnect path also passes no playerId/name/dogType on the WS URL, so every reconnect - and arguably every first connection, since createRoom POSTs but then opens a stateless WS - creates a fresh anonymous identity from the DO's perspective; the REST-layer playerId is thrown away. The simulation port itself is passable but went from 60Hz to 20Hz without a single real two-client playtest; behavioral drift on rotation smoothing, reconciliation, and boid dynamics is plausible. The cooperative HUD sheep counter will read zero the entire match because of an adapter routing bug. Gate visuals in competitive mode will never render. The prior agent's "C4 cutover complete" status is not defensible - this was shipped on curl smoke tests against `/api/lobbies` and `/api/leaderboard` only. Rollback claim ("one DNS flip") also misrepresents reality: the `VITE_USE_DO_BACKEND` flag is build-baked, so rollback is rebuild-and-redeploy.
